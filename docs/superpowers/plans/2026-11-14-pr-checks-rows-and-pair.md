# The PR's checks list what it waits for, and a search PR's pair starts by itself (5 PRs)

Owner, 14 Nov 2026 (relayed by sa): "why I don't see the search pair as a PR CI check?"; "when I click on 'All checks passed' … It doesn't show the e2e running. It shows just green"; asked via AskUserQuestion: "Yes, only when search files change (Recommended)", then "I want all the PRs like that, to start the pair by themselves, and to see the check at the PR level, and to see the outcome results as a PR comment".

## Design (states / one owner / verdicts)
- **Rows (1/5):** `pr-verdict.py` alone writes. One check row per counted by-hand run (the PR's e2e) on the PR's current open head, a pure function of (counted runs, the verdict's state). Rows are never required; the one required check stays "All checks passed". An ending run is looked at again until it completes.
- **One pair per PR at a time (2/5):** the pair workflow's own concurrency group replaces the older pair of a PR (`release` and `status` run on a cancel: claims back, row "superseded", grey). A head that moved only by files the search does not read keeps the numbers (the comment says which commit was measured and that it stands).
- **One starter (3/5):** the PR verdict starts the pair (`tools/pr_verdict_pair.py`, run by `pr-verdict.py` after each verdict), once per head that changes a search file (`SEARCH_FILES`, `tools/pr-body-check.py`), at most 4 starts per PR per 24 h; people come from the body's Moves lines, else the last pair's people (kept in the pair comment's last line), never a guess. Verdicts, in order: the head already has its row, nothing; a head that moved from the measured one by no search file, the row is copied ("ran on <sha7>, search files unchanged since"); `Moves: nothing (...)` and no people, a green row "nothing"; no people, a row "pair needed: name the people in the body's Moves lines"; 4 starts in 24 h, a row "pair limit" with the command; otherwise the row "pair queued" first, then the dispatch (a failed dispatch moves the row to "pair not started", tried again after 3 min). A `waiting` row whose dispatch never happened is started again. `tools/ship-search-hold.sh` keeps only the hold and loses its dispatch.
- **The row decides (4/5):** `pair_row.decide` ends the row good or bad by rule: a Moves-line person claiming a gain needs a gain above their usual difference (band floor 7), else red "no proven gain" after the pair's single rerun; a pair that is not valid twice is red "not valid twice: <reason>".
- **The verdict reads the row (5/5):** no row, queued, running, neutral or "pair needed" keeps "All checks passed" pending with the row's words; red fails it; green counts green. The pair's closing job dispatches the verdict so the status is rewritten at once. The DONT MERGE / `search-hold` plumbing is removed, after the gate is seen working on one named live search PR.
